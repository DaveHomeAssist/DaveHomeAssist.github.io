Step 1 of 5 · Cheap route

Gear up

What to bring for this route, and what bites.

Capture kit

Cue log
A laptop running a free MIDI monitor behind a USB MIDI interface: MIDI Monitor on a Mac, Protokol on Windows, or ReceiveMIDI from the command line. Feed it from a thru box or a spare output so the show line stays intact.
Stage picture
A phone on a clamp or tripod with the whole playing area in view. Power it, switch to airplane mode and record 1080p continuously.
Cue log
A listen-only tap on the show network: join the network MIDI session, or have playback send its OSC to Protokol. Pull the media server's own log too, so you have what it ran beside what it received.
Stage picture
A network camera on a locked preset, recorded with OBS Studio. Record the media server's program output as a second feed: one shows what was sent, the other what landed.
Cue log
The log from your capture route, with cue labels spelled exactly as they are on the cue sheet. Software can only match what's written the same way.
Stage picture
Stills at the same offsets for every firing, from a camera that never moves. A change in framing or exposure reads as a change on stage.

Clock and storage

One clock
The laptop's clock, filmed by the phone at the start and end of the run. Use a clock display that shows fractions of a second.
Storage
Room on the phone for the whole run (1080p takes a few gigabytes an hour) and somewhere to offload it afterward. A spreadsheet is enough for the notes, and LosslessCut is a free way to step through the clip and save stills.
One clock
One NTP source for compatible machines, or LTC timecode recorded on a camera audio channel. Confirm how each recorder timestamps frames and measure offset, latency and drift.
Storage
A capture machine or NAS sized for every feed for the whole run, on a network segment that can carry the video.
One clock
Whatever your capture route uses. Software can't repair timestamps that were never lined up.
Storage
Space for stills, drafts, and the prompt or thresholds you used. Keep the cue sheet as text or CSV: cue number, label, intended look.

Watch out

  • Phones overheat, take calls and stop at storage limits. Check at every break.
  • Autofocus and auto-exposure hunt under stage light. Lock both.
  • 4K and high frame rates fill storage without making a cue easier to judge.
  • If cues travel over USB or the network, there's no cable to split. Run the monitor on the receiving computer.
  • Listen, don't control. Some devices take one control connection at a time, so an extra client can knock the show's own session off.
  • Video streams can consume substantial bandwidth. Confirm network capacity with the system owner and keep capture traffic from disrupting show control.
  • Keep the capture machine out of the control path. If it dies, the show shouldn't notice.
  • Software flags what looks different, and a scene look can look like a fault.
  • Take timing from the logs, never from a model's description.
  • Cloud models mean frames leave the building. Local analysis keeps them in-house.

Step 2 of 5 · Cheap route

Set up and test it

Tap the feed, frame the shot, sync the clocks, then prove it end to end.

Listen without touching

Set the logger to receive-only, and keep the raw messages beside any decoded labels.

Use a buffered MIDI THRU box or spare output into the laptop's interface. Do not use a passive Y cable. Check which messages carry cue numbers: MIDI Show Control does. Notes and program changes need a mapping you write down.

Join the network MIDI session as a listener, or have playback send OSC to your logger on each cue. Open no extra control sessions to show devices.

Use the same tap as your capture route. Make the decoded labels match the cue sheet, so cue 42.1 in the log is cue 42.1 on the sheet.

Frame it, lock it, check the recording

Get the surfaces the team cares about in frame. Judge focus, exposure and motion from the recording, not the viewfinder.

Lock the phone's focus and exposure so lighting changes stay visible. Clamp it where nobody will bump it, and mark the spot.

Recall one camera preset and lock control for the whole show. Turn off continuous autofocus and set focus by hand.

Frame for the software: the same shot every run, with the areas it measures clear of heads and masking.

Sync the clocks

Keep original timestamps and record a visible clock reference. Measure offset and drift. A test cue checks the full chain, but its response includes cue, camera and recording delay; do not treat all of that as clock offset.

Film the laptop's clock for a few seconds at the start and again at the end. The two readings give you the offset and any drift.

Use the approved NTP source or record LTC on the camera's audio. Verify how that reference maps to recorded frames at both ends of the run.

Do this on the capture route, then hand the software the measured offset as a number. Don't let it estimate one.

Example offset note
Camera −0.42 s vs logger
Measured 18:55 · ±0.05 s

Run a full test

Fire a known test cue. Find it in the saved log with the right source and label, then open the actual clip or stills.

Use the recorded clock reference to map the logged firing into the clip. If the expected change is missing, check clock alignment, response delay and capture gaps before the run.

Let the capture script grab its stills unprompted: a trigger frame plus +1, +2 and +3 s suits short transitions. A rolling buffer shows what happened before the GO.

Push the test firing through the whole pipeline and check the draft against the frame yourself. Give the software a reference frame for each scene look.

During the run

Two feeds, watched separately.

Watch the log and the picture as two feeds

Cue log

A quiet stretch with no cues is normal. Check the logger's connection or heartbeat if it has one.

Picture

Make sure the camera still shows live motion and hasn't frozen.

At every break, look at the phone: still recording, not hot, storage left.

Watch the recorder's inputs and the clock status. When program out and the camera disagree, that's a finding to log, not a fault to chase.

A live watcher will flag frames mid-show. Note the time and keep going. Judging them is for review.

Timestamp every interruption

Keep a timestamped run-notes file or spreadsheet. Record the run ID, date, time zone, operator, sources and start time, then every hold, restart, skipped cue and capture gap.

Read times off the laptop clock you filmed, so the notes and the log agree.

Review

Turn the log and footage into notes the team can trust.

Each source answers a different question, so don't let one stand in for another.

One entry per firing

Every firing gets its own entry, including repeats during notes or pickups. Map each logged firing into the clip using the clock reference, and write what you see. Stills arrive filed by cue and firing. Your job is the observation. The software drafts each one. Confirm, correct or reject every draft.

Mac recorder

Record a rehearsal on one Mac

Use one MIDI input and one picture source per recording. The app records a silent 640 × 360 H.264 movie and JPEGs for MIDI Show Control (MSC) GO messages. Cue numbers stay text. Two firings of 68.10 get separate images. The other gear and AI suggestions in the guide are optional.

Install once

Use macOS 14 or later with Apple's Command Line Tools. Open Terminal, run xcode-select -p, and, if it reports no tools, run xcode-select --install and finish Apple's installer. In Finder make a folder called Rehearsal Capture Kit in Downloads. In the HTML guide open Mac recorder and use the Save buttons to put Capture.m, Info.plist and build.command there. Keep their filenames. If you already extracted the source kit, use its folder instead.

In Terminal type cd (including the space), drag the folder from Finder into Terminal, press Return, then run:

/bin/zsh build.command --open

This builds and opens the app. Each build goes into its own Build folder inside Rehearsal Capture Builds, in the Applications folder of your home folder. Terminal prints the app's location and a ready-made open line. Paste that line to open the app for later runs, or open the app from the newest Build folder in Finder. The first build requires the tools. USB, QuickTime and practice subsequently work offline. For the RTSP source also install FFmpeg from Homebrew with brew install ffmpeg; the app checks /opt/homebrew/bin/ffmpeg and /usr/local/bin/ffmpeg. Install the optional tool before rehearsal. Official references: developer.apple.com/xcode/resources, brew.sh, ffmpeg.org.

Prove the software first

Open the app and choose Practice with generated cues and video. Choose a writable folder on a disk with room for the session. Watch for a changing picture, two GO firings and a growing frame count. Wait at least ten seconds, then choose Stop and save. In the new Capture folder, open rehearsal.mov in QuickTime Player. Look for continuous changing color and eight JPEGs (two firings, four offsets each). Each firing should say 68.10 in events.jsonl. Practice opens no camera or MIDI input. Quit and reopen the app for each new session.

Connect MIDI

Ask the console or playback operator for the duplicate cue output. Wire its spare MIDI OUT or an isolated THRU-box output to MIDI IN on your USB interface, then connect the interface to the Mac. Leave the interface's MIDI OUT unplugged. For an existing network MIDI session, open Audio MIDI Setup, show MIDI Studio, open the Network MIDI setup, and join the operator-provided session. Leave live routings to show outputs empty. Choose that session's input in the recorder. The app opens a CoreMIDI input port only.

Choose a camera route, select the named MIDI input, then enter the MSC device ID (decimal 0 to 127) or all. Enter the requested photo offsets in seconds, such as 0,1,2,3 or 0,3,6,9. Note On, Program Change and other non-MSC data can appear as raw packets. Only MSC GO creates a firing here. If packet count rises but GO stays at zero, confirm message type and device ID with the operator.

Connect the picture

USB or HDMI. Connect the camera's USB video output, or connect HDMI OUT to an HDMI-to-USB capture device and plug that into the Mac. Use clean HDMI if available. Select the USB route and then the camera or capture device by name. Allow Camera access. If it is absent, confirm that macOS sees it in QuickTime Player's New Movie Recording camera menu, close the preview to release the device, and reopen the app.

iPhone through QuickTime. Connect and unlock the iPhone. If asked, trust the Mac. In QuickTime Player choose File > New Movie Recording. Select the iPhone in the camera menu and confirm a moving stage image. If the USB connection offers the phone screen, open the phone camera and check what the preview actually shows. Leave the preview open, unobscured by controls, with its pointer outside the picture. Choose the iPhone route and select that QuickTime window. Grant Screen & System Audio Recording permission to the recorder if macOS asks, then reopen it. The recording contains the window's visible picture, including any overlays. A camera selectable directly in macOS can also use the USB route.

Network camera. Ask the camera operator for a read-only RTSP stream reachable from the recording Mac, and confirm a second viewer is supported. Use the RTSP URL supplied by the operator, including its port and path. This version supports RTSP over TCP with a credential-free URL. For a camera requiring credentials, use an approved read-only relay or take its HDMI output through a capture device. Select Network camera and enter the stream URL. The recorder reads video only and provides no PTZ controls. A frozen picture, interleaved transport failure or an unsupported codec calls for checking the approved stream with the operator.

Sync and verify on the recording Mac

  1. Choose the session disk. Starting creates a unique Capture folder. Check framing, focus and exposure on the recorded picture. Keep the Mac on power, prevent sleep and budget storage from a representative sample (sample bytes × planned minutes / sample minutes, plus spare room).
  2. Have the operator fire the same known rehearsal cue twice with a visible change in frame. For alignment, also film a time display or a slate visible on cue. Write down the cue label, planned offsets and expected visual change. Keep recording through the largest offset plus one second.
  3. Stop and save. Check for two distinct firing numbers, the exact cue/list text, moving video and the expected JPEGs. Open images.jsonl in a text editor. Each saved row names its file, actual host time, movie position and lateness. Seek the movie to movieSeconds and compare the stage look with the JPEG. A missing slot has a reason. Compare a second sync reference near the end of a long run to check drift. A logged GO proves receipt; use the image to judge the stage.
  4. USB timestamps use sample PTS converted to Mac host time. QuickTime timestamps belong to the delivered window frames. RTSP uses arrival after decoding, which includes network and decoder delay. Compare the filmed reference with the log to estimate timing uncertainty for each setup. A visual cue can include stage response latency. Record any measured delay alongside the archive. The recorder does not automatically correct camera latency.
  5. If the camera stalls, check the age of the last frame and the saved movie. If MIDI continues, the listener can still log cues. Restore the source outside the recorder and start a fresh session if reconnection is necessary. Preserve the interrupted folder and mark the gap. Empty slots are preferable to assigning an unrelated frame.

Recover and hand off

Stop only after the last photo window. Open the movie and JPEGs directly from a copy of the whole Capture folder. Keep the JSONL logs with them. Each line is a separate record; events.jsonl groups by firing number, and images.jsonl maps the firing and requested offset to the saved filename. checksums.json contains SHA-256 hashes of the files at stop. Compare the originals and copy before deleting or moving anything. A forced quit or full disk can leave an unfinished movie; keep the raw logs and start a new folder for the next attempt. This recorder does not resume an interrupted movie or combine separate runs.

Automated replay (optional)

The replay opens no camera or MIDI input. It closes during its third cue to exercise the missing-image case. Expected result is 55 frames, three separate firings of 68.10, nine saved images and three missing slots. The verifier needs Python 3 and FFmpeg.

In the HTML guide use Save verify.py to put verify.py in the Rehearsal Capture Kit folder. The source kit already includes it. In Terminal, in that folder, make a fresh test folder:

mkdir -p Practice

Paste the automated replay line that build.command printed. It contains the full path of the built app and ends in --self-test Practice. If that Terminal output is gone, run /bin/zsh build.command again to build a fresh copy and print a new line. The replay finishes within a few seconds and creates a Capture folder inside Practice.

Copy that Capture folder to another location. In Terminal type python3 verify.py (including the space), drag the copy from Finder into Terminal and press Return. The verifier compares the frame identifiers in the movie and all nine JPEGs, and prints a line beginning with PASS. The manual practice check above works without the verifier.

static void packet(NSData *d,double t,UInt64 ticks,double received){
    if(!active)return;
    row(@"midi.jsonl",@{@"packet":@(++packets),@"input":inputName,@"sourceHostTicks":@(ticks),@"hostSeconds":@(t),@"receiptHostSeconds":@(received),@"hex":hex(d.bytes,d.length)});
    const uint8_t *b=d.bytes;
    for(NSUInteger i=0;i<d.length;i++){
        uint8_t c=b[i];if(c>=0xf8)continue;
        if(c==0xf0)fragment=[NSMutableData new];
        else if(c>=0x80 && c!=0xf7){fragment=nil;continue;}
        if(!fragment)continue;
        [fragment appendBytes:&c length:1];if(fragment.length>65536){fragment=nil;continue;}
        if(c!=0xf7)continue;
        NSData *msg=fragment;fragment=nil;const uint8_t *v=msg.bytes;
        if(msg.length<7||v[1]!=0x7f||v[3]!=2||v[5]!=1)continue;

        NSString *cue=[fields.firstObject length]?fields.firstObject:@"current";

    }
}

verify.py
"""Verify a copied --self-test session using FFmpeg and Python 3."""
import hashlib
import json
from pathlib import Path
import subprocess
import sys

root = Path(sys.argv[1])
def rows(name):
    return [json.loads(line) for line in (root / name).read_text().splitlines()]

def decoded_frame(path, time=None):
    args = ['ffmpeg', '-v', 'error', '-i', str(path)]
    if time is not None:
        args += ['-ss', f'{time:.5f}']
    raw = subprocess.check_output(args + ['-frames:v', '1', '-vf', 'scale=64:36',
                                          '-pix_fmt', 'gray', '-f', 'rawvideo', 'pipe:1'])
    assert len(raw) == 64 * 36, (path, time)
    return sum(1 << bit for bit in range(6) if raw[18*64+bit*10+4] > 128)

for name, digest in json.loads((root/'checksums.json').read_text()).items():
    assert hashlib.sha256((root/name).read_bytes()).hexdigest() == digest
events = rows('events.jsonl')
assert [row['cue'] for row in events] == ['68.10'] * 3
assert len({row['firing'] for row in events}) == 3
assert len(rows('frames.jsonl')) == 55
images = rows('images.jsonl')
saved = [row for row in images if row['status'] == 'saved']
assert len(images) == 12 and len(saved) == 9
for row in saved:
    expected = row['frame'] - 1
    assert decoded_frame(root/row['file']) == expected
    assert decoded_frame(root/'rehearsal.mov',row['movieSeconds']) == expected
    assert 0 <= row['lateBySeconds'] <= 0.75
assert {row['offset'] for row in images if row['status']=='missing'} == {1, 2, 3}
print('PASS: hashes, 3 repeated decimal cues, 55 video frames, 9 exact image/movie matches, 3 missing slots.')
